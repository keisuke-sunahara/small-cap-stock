### 2026-10-04 / 【承認が必要】継続保有の判断の時点（基本ルールの文面には時間の矛盾がある）
- 問題：基本ルールでは「翌週も上位N銘柄に選ばれた保有銘柄は売らない」。しかし翌週の上位Nは最終営業日の**引け後**の予測で決まり、引成の売り注文はその日の**引け前**（11:30〜15:00）に入れる必要がある。文面どおりに再現すると「引け値を見てから、引けで売るかを決める」ことになり、実際には発注できない（わずかな未来情報の混入）
- 暫定の扱い（フェーズ2の承認まで）：**最終営業日の前の営業日の引け後の順位で継続を判断する（`continuation: prev_day`）**。ユーザーは週に2回（木曜の夜と金曜の夜）予測を見ることになる
- 比較のため、設定で切り替えられるようにした：`none`（毎週すべて売る）、`prev_day`、`same_day`（文面どおり・実行不可・参考値）
- 継続を判断するときの「上位N」は、保有銘柄は100株を買えるかの判定なしで数え、保有していない銘柄は買えるもの（100株・売買代金の上限）だけを数える
- 他の選択肢：週の予測自体を木曜の引け後に移す（予測が1日古くなる）、継続保有をやめる（コストが増える）

### 2026-10-04 / ベースライン4（ユニバースの等金額平均）の計算方法
- 30万円では全銘柄を買えないため資金制約は適用しない。売買のタイミングと約定の判定（寄付の指値、最終営業日の終値）は同じにし、約定しなかった銘柄の分は0%として等金額で平均する。営業日が1日の週は0%
- コストなし・0.3%・0.5%の3通りを出す。**超過リターンの基準には「コストなし」を使う**（コストありは毎週すべてを売買し直す前提で年率−26%になり、比較の基準として甘すぎるため）

### 2026-10-04 / 評価の細部
- 週：月曜始まりの暦の週（ISO 週）。予測日は前の週の最終営業日
- 相場環境：暦の四半期ごとの TOPIX の騰落率が +5% 超を「上昇」、−5% 未満を「下落」、その間を「横ばい」とする（分析用で、売買には使わない）
- 税引き後：年ごとの利益がプラスなら 20.315% を引く（損失の繰越控除は考えない簡易版）
- 学習用の目的変数は「翌営業日の始値 → 5営業日後の終値」で確定（終値が無い日は直前の終値、上場廃止なら最後の終値。上場廃止の銘柄を落とすと生存者バイアスになるため）

### 2026-10-04 / 比較用に「予算固定」の成績を併記する（ユーザーの依頼）
- 決めたこと：`backtest.budget_mode` を追加。`min_equity`（基本ルール：min(30万円, 総資産) ÷ N）を主とし、`fixed`（毎週の予算を30万円 ÷ N に固定し、その週の損益 ÷ 30万円 を週次リターンとする。現金のマイナスは補充したとみなす）を戦略の比較用に併記する。`fixed` の最大ドローダウンは週次リターンを複利でつないだ推移で計算する
- 理由：基本ルールでは負けると予算が縮み、50円台の超低位株しか買えなくなる連鎖が起き、戦略の良し悪しの比較が経路に左右される（モメンタムでは注文の順位の平均が105位、指値の中央値が114円。予算固定では約5位・515円）
- 他の選択肢：基本ルール自体を変える（承認が必要）、Rank IC だけで比べる（売買の制約を反映しない）

### 2026-10-04 / 上場廃止が決まった銘柄を、その時点の情報で見分けられるかの調査（ユーザーの依頼。ルールには使っていない）
- 方法：J-Quants の銘柄一覧の貸借信用区分（1:信用、2:貸借、3:その他）。公式仕様では、日付を指定するとその時点の情報が返る。日付 d の一覧は d の前の営業日の 17:30 頃に公開されるので、予測日 p の一覧は p の引け後に確実に分かる（`src/analysis/phase2_delisting_signal.py`、`reports/phase2_delisting_signal.json`）
- 結果の要点：上場廃止になった普通株616銘柄のうち69%が、最後の上場日に「その他」。変わったのは中央値で廃止の16営業日前（95%が10営業日以上前）。「その他」で見つからなかった廃止は合併・株式交換などが多いとみられる（最後の20営業日の値動きの中央値 5.6%）
- 誤検出：新規上場の直後（1日程度）と、債務超過などで上場廃止の猶予期間に入った銘柄（長いものは1年以上「その他」のまま）。予測日のユニバース内の「その他」のうち、30営業日以内に廃止は21%（それ以外の銘柄は0.17%）

### 2026-10-04 / GitHub への送信が止まった原因と対処

### 2026-10-04 / 改行コードの固定（ユーザーの依頼）
- 決めたこと：`.gitattributes` に `* text=auto eol=lf` を置き、テキストはリポジトリ内で LF に統一する。画像・Parquet などはバイナリ指定。`.bat`・`.cmd` は CRLF
- 理由：Windows のツールが CRLF で書き出すと、改行コードの違いだけでファイル全体が変更扱いになり、記録が書き換えられていないかを差分で確認しにくくなるため
- 既存のファイルは正規化しない（`git add --renormalize` は実行しない）。CRLF でコミット済みの11件（`docs/PROGRESS.md`・`reports/phase2_baselines.json` など）と CRLF・LF 混在の1件は、`text=auto` の仕様で変換されず、中身もハッシュも変わらない。評価役が検証中の数字のファイルを変えないため。追加後の `git status` で既存ファイルに変更がないことを確認した
- 他の選択肢：全ファイルを LF に正規化する（既存の記録のバイト列が変わるので不採用）、`core.autocrlf` の設定だけで対応する（各自の環境の設定に依存し、評価役の環境で再現されないので不採用）
